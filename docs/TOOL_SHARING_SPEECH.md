# TestCaseMind 工具分享演讲稿

大家好，今天想和大家分享一个我最近在做的测试效率工具：TestCaseMind。

它的定位很简单：这是一个 AI 驱动的测试用例设计智能体。我们给它一份需求文档，它可以自动完成需求质量评审、测试点生成、测试用例展开、测试资产导出，并且把过程中沉淀下来的经验持续写入知识库和长期记忆里。

我今天主要从五个部分来介绍：第一，为什么要做这个工具；第二，它整体是怎么设计的；第三，实际怎么使用；第四，目前能看到什么效果；第五，后续还可以怎么继续优化。

## 一、工具诞生的原因

先说为什么做。

在日常测试工作里，我们经常会遇到几个非常典型的问题。

第一个问题是需求文档质量不稳定。有些需求写得很完整，背景、业务规则、边界条件、异常处理、字段口径都比较清楚；但也有不少需求只描述了主流程，隐含规则、历史逻辑、异常场景、上下游依赖都没有明确写出来。测试同学在设计用例前，往往要先花很多时间做需求理解和需求反问。

第二个问题是测试设计依赖个人经验。资深同学看到一个需求，会自然联想到历史问题、边界值、枚举值、表字段、批处理异常、金额精度、数据同步延迟等风险点。但这些经验通常分散在个人脑子里、历史用例里、缺陷记录里，很难稳定复用。新人或者不熟悉业务域的同学，很容易漏掉这些隐含测试点。

第三个问题是用例生成链路比较长。一个需求从评审、拆测试点、补充风险点、展开用例、整理 Excel、写测分报告，到最后沉淀经验，整个过程有很多重复劳动。尤其是金融风控类需求，规则细、字段多、计算逻辑多，手工展开会消耗大量时间。

第四个问题是 AI 直接生成用例虽然快，但质量不可控。如果只是把需求丢给大模型，让它一次性输出测试用例，经常会出现几个问题：来源不可追溯、用例粒度忽大忽小、测试点和用例一比一展开、没有结合本地知识库、没有记忆历史经验，也没有中途失败后的恢复能力。

所以 TestCaseMind 想解决的不是“让 AI 随便写一批用例”，而是把测试设计这件事做成一个可追踪、可恢复、可积累的工程化流程。

它的目标可以概括成四句话：

第一，把需求文档转成可以评审、可以交付的测试资产。

第二，把测试点来源标清楚，区分哪些来自需求本身，哪些来自知识库补充，哪些来自风险经验推断。

第三，让工具越用越懂业务，通过知识库和长期记忆沉淀历史测试经验。

第四，让长耗时任务也能稳定运行，失败了能续跑，结果能落盘，过程能排查。

## 二、工具架构介绍

接下来介绍一下整体架构。

TestCaseMind 不是一个单 prompt 工具，而是一个带工作流编排、技能系统、知识库、长期记忆和任务状态管理的测试智能体。

从大的层次看，它可以分成六层。

第一层是入口层。

目前有两个入口。一个是命令行入口，也就是 `scripts/agent.py`；另一个是 MCP Server 入口，也就是 `scripts/mcp_server.py`。命令行适合本地直接执行，MCP 入口适合接入 Claude Code，通过自然语言触发工具。

第二层是工作流编排层。

主流程分成四个阶段：

第一阶段是需求评审。系统会先评估需求文档质量，输出质量等级、评分、问题清单和评审思维导图。

第二阶段是测试点生成。系统会从需求中提取测试点，同时结合知识库和风险经验补充需求里没有直接写出来的测试点。

第三阶段是测试用例展开。系统会把测试点展开成可执行用例，不限制一个测试点只能对应一条用例，而是根据业务路径、枚举值、边界值、异常分支展开成多条用例。

第四阶段是本地导出。系统会生成 Markdown、Excel、XMind Markdown 和底层 JSON，既方便人看，也方便程序后续续跑和集成。

第三层是 Agent Harness 机制。

这个项目是基于 learn-claude-code 的思路构建的，组合了多个 Harness 机制。

比如计划展示机制，Agent 在执行时会先列出计划，让用户知道它在做什么。

比如技能加载机制，需求评审、测试点生成、测试用例生成都有独立的 skill 文件，相当于把不同任务的专家提示词模块化。

比如上下文压缩机制，长文档不会一次性粗暴塞进去，而是按章节、按任务拆分，减少上下文浪费。

比如任务持久化机制，每次运行都会写任务状态和 manifest。即使中途失败，也可以恢复。

还有长期记忆和容错降级机制。长期记忆用于沉淀领域经验；容错降级用于保证某个阶段失败时，整个流程尽量不中断。

第四层是知识增强层。

这个部分非常关键。因为需求文档本身往往写不全，所以系统会把表设计、字段定义、枚举值、开发设计文档、历史规则等规范性资料放入 `knowledge_base/`，并通过本地向量检索进行 RAG 增强。

这样生成测试点时，模型不只看当前需求，还会检索相关知识，补充字段约束、数据来源、计算口径、异常路径和历史风险。

第五层是记忆层。

知识库更像是稳定的业务资料，而记忆层更像是测试经验积累。比如哪些模式经常出问题，哪些质量信号需要关注，哪些用例被人工评审后认为不应该纳入用例库，这些都可以逐步沉淀。

第六层是交付层。

系统最终不是只输出一段文本，而是输出一组可交付资产，包括需求评审报告、问题清单 Excel、评审思维导图、测试点思维导图、测试用例 Excel、测分报告，以及给程序使用的 JSON 和 manifest。

这里有一个设计原则：从用户视角，可读文档优先；从系统视角，保留结构化 JSON。也就是说，人主要看 Markdown、Excel 和 XMind Markdown，程序继续用 JSON 做续跑、统计和集成。

## 三、工具使用介绍

下面说一下实际怎么用。

第一次使用时，需要先把项目下载到本地：

```bash
git clone https://github.com/Joeyzheng001/TestCaseMind.git
cd TestCaseMind
```

然后建议创建独立 Python 环境，安装依赖：

```bash
conda create -n testcase-mind python=3.12
conda activate testcase-mind
pip install -r requirements.txt
```

这里不建议直接用 base 环境，因为 base 里可能混入其他项目的依赖，比如音视频相关的 torchcodec、FFmpeg 动态库等，容易影响文本 RAG 初始化。

然后配置 `.env`，填入模型 API Key 和模型配置。

如果要使用知识库增强，还需要准备知识库。比如把表设计、字段定义、开发设计文档转换进 `knowledge_base/`，再重建向量索引：

```bash
python scripts/kb_from_excel.py 表设计文档.xlsx
python scripts/kb_from_design.py 因子设计文档.xlsx
python scripts/kb_convert.py 技术设计文档.docx
python scripts/kb_rag.py --rebuild
```

日常使用就比较简单了。

如果要对一份完整需求生成测试资产：

```bash
python scripts/agent.py "需求文档.docx" --kb
```

如果只想处理某一个章节：

```bash
python scripts/agent.py "需求文档.docx" --kb --section "5.8 ETF退款金"
```

如果只想生成测试点，不展开用例：

```bash
python scripts/agent.py "需求文档.docx" --kb --no-cases
```

如果中途失败了，可以续跑：

```bash
python scripts/agent.py "需求文档.docx" --kb --resume
```

从使用者角度看，工具会自动完成几件事。

第一，读取需求文档。如果是 Word 文档，会先转换成 Markdown。

第二，如果指定了章节，会只提取对应章节。如果没有找到完全匹配的章节，系统不会擅自选择相似章节，而是提示人工确认。

第三，进行需求评审，生成需求质量评分和问题清单。

第四，生成测试点，并标注来源是 `REQ`、`KB` 还是 `RISK`。

第五，把测试点展开成测试用例，并导出 Excel。

第六，把整个运行过程写入日志，方便后续排查耗时、失败原因和模型返回问题。

最终结果会在 `output/<需求名>/<时间戳>/` 目录下。

常用交付物包括：

`review_report*.md`，这是需求评审报告。

`review_issues*.xlsx`，这是需求问题清单。

`review_mindmap*.md`，这是评审思维导图，可以导入 XMind。

`testpoints_xmind*.md`，这是测试点思维导图。

`testcases*.xlsx`，这是测试用例 Excel，也是最常交付给团队评审的文件。

`report*.md`，这是测分报告。

另外还有 `manifest.json` 和底层 JSON，主要给系统自己做续跑和集成使用。

这里还有一个比较新的能力：测试用例 Excel 里增加了“是否纳入用例库”和“未纳入原因”两个字段。人工评审后，可以标记哪些用例值得进入用例库，哪些不值得。然后通过：

```bash
python scripts/learn_from_case_review.py "testcases.xlsx"
```

系统会总结未纳入原因，反向优化后续用例生成提示词和长期记忆。

这个设计的核心是：不是让 AI 一次生成完就结束，而是把人工评审结果也纳入闭环，让工具持续学习团队的用例标准。

## 四、工具效果展示

接下来讲一下目前可以展示的效果。

第一类效果是需求评审。

工具会先对需求文档进行质量评估，比如从需求完整性、一致性与逻辑性、可测试性、清晰度与规范性、风险与依赖描述几个维度给出评分。它不只是说“这个需求还可以”，而是会列出具体问题，比如字段口径不清楚、异常路径缺失、边界条件没有说明、上下游依赖没有描述、预期结果不可测等。

这对需求评审会比较有帮助。测试同学可以提前拿到一份问题清单，在评审会上逐条确认，而不是临场靠经验提问。

第二类效果是测试点生成。

测试点会分来源。

`REQ` 来源表示这个测试点来自需求文档本身。

`KB` 来源表示这个测试点来自知识库补充，比如数据字典、枚举值、字段约束、开发设计里的实现逻辑。

`RISK` 来源表示这个测试点来自风险推断，比如金额精度、并发处理、外部依赖失败、批量数据边界等。

这种来源标记很重要。它让我们知道一个测试点为什么会出现，是需求明确写了，还是工具结合知识库和测试经验补出来的。后续评审时，也更容易判断它是否合理。

第三类效果是测试用例展开。

过去我们遇到过一个问题：一个测试点只生成一条用例，最后看起来测试点和用例是一比一的。这其实不符合真实测试设计。现在提示词已经调整成按业务路径、分支、枚举值、边界值、异常场景展开。

比如一个金额计算类测试点，正常情况下至少应该覆盖单笔计算、多笔汇总、金额为 0、小数精度、负向或无数据场景、无关类型数据过滤等。它不应该只生成一条“正常计算”的泛化用例。

第四类效果是可读交付。

以前很多 AI 工具输出 JSON，看起来结构化，但不方便业务评审。现在系统保留 JSON 给程序使用，但面向人交付的是 Markdown、Excel 和 XMind Markdown。评审报告可以直接阅读，问题清单可以在 Excel 里筛选，用例可以直接评审和修改，思维导图可以导入 XMind。

第五类效果是工程化可排查。

系统现在会生成运行日志，记录每个阶段的耗时、RAG 检索情况、模型调用步骤和错误信息。比如如果知识库检索失败，不会只在终端闪过一段长错误，而是会写入 `logs/`，方便后续定位。

同时，manifest 会记录本次运行生成了哪些文件、各阶段耗时是多少、使用了哪个模型、是否启用了知识库等信息。这对于后续做性能优化和质量分析很有帮助。

第六类效果是经验闭环。

知识库、长期记忆、人工用例库评审，这三个机制会让工具不是一次性的。每跑一次需求，都可以把通用规则沉淀下来；每评审一次用例，都可以把“哪些用例不该进用例库、为什么不该进”反馈给系统。长期看，工具会越来越贴近团队自己的测试标准和业务域。

## 五、后续优化畅想

最后说一下后续可以继续优化的方向。

第一个方向是增加代码 Review Skill，用开发代码反向补充测试点。

现在主要输入还是需求文档和知识库。后续可以增加一个专门 review 开发代码的 skill，让系统读取代码变更，识别需求文档里没有体现出来的测试点。

比如代码里新增了异常分支，但需求没写；代码里修改了某个公共方法，可能影响其他已上线功能；代码里新增了缓存、异步任务、批处理逻辑，可能带来一致性和时序问题。这些都可以转化成补充测试点。

也就是说，未来测试点来源可以从现在的 `REQ`、`KB`、`RISK`，进一步扩展到 `CODE`。这样测试设计就不只基于“需求说了什么”，也能基于“代码实际改了什么”。

第二个方向是打通测试环境，生成自动化测试用例。

现在工具主要生成手工可评审的测试用例 Excel。后续可以结合测试环境、接口文档、数据库连接、Mock 平台，把部分用例进一步转成自动化脚本或自动化用例定义。

比如接口类需求，可以自动生成接口请求参数、断言规则、数据库校验 SQL；批处理类需求，可以生成造数步骤、任务触发方式、结果校验方式；页面类需求，可以生成 UI 自动化关键路径。

人工确认后，这些自动化用例可以按需归入自动化回归用例集。

第三个方向是基于代码差异自动挑选回归用例，实现精准回归。

现在回归测试常见的问题是范围不好控制。测少了担心漏测，测多了成本太高。未来可以把代码 diff、需求模块、接口变更、数据库表变更、历史缺陷和用例标签打通。

当代码发生变化时，系统自动分析影响范围，挑选出最相关的一组自动化回归用例。比如某个公共计算函数变了，就回归所有依赖这个函数的因子；某张核心表结构变了，就回归所有读取这张表的规则；某个接口字段变了，就回归上下游消费这个字段的场景。

这样回归测试就可以从“凭经验选一批”逐步变成“基于变更影响分析精准选择”。

第四个方向是建立团队级质量反馈闭环。

比如我们可以统计哪些类型的需求经常出现可测试性问题，哪些模块经常缺边界条件，哪些用例经常被人工评审剔除，哪些 RISK 测试点最后证明是有效的。这些数据可以反过来指导需求模板优化、开发设计规范优化和测试策略优化。

第五个方向是进一步优化执行性能。

当前工具已经做了一些并行化、章节过滤、缓存和日志统计。后续可以继续做更细粒度的优化，比如针对完整文档做智能章节分组，减少重复上下文；对 RAG 检索结果做缓存；对低风险章节采用轻量模式；对高风险章节采用深度模式。但这里有一个原则：性能优化不能牺牲输出质量。测试设计工具最重要的不是生成得快，而是生成得准、生成得全、生成得可评审。

## 六、总结

最后总结一下。

TestCaseMind 解决的核心问题，不是简单地“用 AI 写测试用例”，而是把测试设计变成一个工程化、可追踪、可恢复、可积累的智能流程。

它从需求评审开始，先判断需求能不能测、哪里不清楚；然后结合需求、知识库和风险经验生成测试点；再把测试点展开成可执行测试用例；最后输出可读交付物，并把人工评审结果和通用规则沉淀回知识库和长期记忆。

从短期看，它可以减少测试设计中的重复劳动，提高需求评审和用例设计效率。

从中期看，它可以沉淀团队经验，让不同同学在同一业务域里的测试设计质量更稳定。

从长期看，它有机会和代码 review、自动化测试、精准回归打通，形成从需求到代码、从测试设计到自动化执行、从执行结果到经验沉淀的完整闭环。

这也是我觉得这个工具最有价值的地方：它不是替代测试同学做判断，而是把测试同学的经验结构化、流程化、可复用化，让大家把更多精力放在真正需要判断力的地方。
